API Changes for 3.11.0[#](https://matplotlib.org/stable/api/prev_api_changes/api_changes_3.11.0.html#api-changes-for-3-11-0 "Link to this heading")

====================================================================================================================================================

[Behavior Changes](https://matplotlib.org/stable/api/prev_api_changes/api_changes_3.11.0.html#id1)
[#](https://matplotlib.org/stable/api/prev_api_changes/api_changes_3.11.0.html#behavior-changes "Link to this heading")

---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------

### `pyplot.subplot` and `pyplot.subplot_mosaic` raise _ValueError_ on existing figures[#](https://matplotlib.org/stable/api/prev_api_changes/api_changes_3.11.0.html#pyplot-subplot-and-pyplot-subplot-mosaic-raise-valueerror-on-existing-figures "Link to this heading")

Passing a _num_ argument to [`subplots`](https://matplotlib.org/stable/api/_as_gen/matplotlib.pyplot.subplots.html#matplotlib.pyplot.subplots "matplotlib.pyplot.subplots")
 or [`subplot_mosaic`](https://matplotlib.org/stable/api/_as_gen/matplotlib.pyplot.subplot_mosaic.html#matplotlib.pyplot.subplot_mosaic "matplotlib.pyplot.subplot_mosaic")
 that refers to an existing figure or is a `Figure` instance now raises a [`ValueError`](https://docs.python.org/3/library/exceptions.html#ValueError "(in Python v3.14)")
.

These utility functions are intended strictly for the creation of new figures and subplots. Previously, they accidentally allowed the reuse of existing figures because they internally called [`figure`](https://matplotlib.org/stable/api/_as_gen/matplotlib.pyplot.figure.html#matplotlib.pyplot.figure "matplotlib.pyplot.figure")
. This change ensures that these functions strictly follow their documented purpose of creating new figures.

To reuse an existing figure, clear it first using `clear=True`:

fig, axs \= plt.subplots(num\=1, clear\=True)
\# or
fig, axd \= plt.subplot\_mosaic(\[\['A', 'B'\]\], num\=1, clear\=True)

If you have a `Figure` instance and want to add subplots to it, use the object-oriented API:

fig.subplots(nrows\=2, ncols\=2)
\# or
fig.subplot\_mosaic(\[\['A', 'B'\]\])

### Complex layouts and constrained layout[#](https://matplotlib.org/stable/api/prev_api_changes/api_changes_3.11.0.html#complex-layouts-and-constrained-layout "Link to this heading")

Constrained layout now produces smaller spacing between subplots in some circumstances. This should only affect complex layouts where rows or columns contain different numbers of subplots, for example a layout created with `plt.subplot_mosaic('AC;BC', layout='constrained')`.

### Bivariate colormaps now fully span the intended range of colors[#](https://matplotlib.org/stable/api/prev_api_changes/api_changes_3.11.0.html#bivariate-colormaps-now-fully-span-the-intended-range-of-colors "Link to this heading")

Bivariate colormaps generated by `SegmentedBivarColormap` (e.g., `BiOrangeBlue`) from a set of input colors now fully span that range of colors. There had been a bug with the numerical interpolation such that the colormap did not actually include the first or last colors.

### Rendering of images now more accurate[#](https://matplotlib.org/stable/api/prev_api_changes/api_changes_3.11.0.html#rendering-of-images-now-more-accurate "Link to this heading")

There have been several fixes to improve the accuracy of how images are resampled and placed during rendering. Some inaccuracies were up to a pixel off in the output. The most apparent improvement is that the alignment of data pixels with tick marks and grid lines is now reliable. Nearly all image output has changed, but often only at a subtle level that is not obvious qualitatively.

### _alpha_ parameter handling on images[#](https://matplotlib.org/stable/api/prev_api_changes/api_changes_3.11.0.html#alpha-parameter-handling-on-images "Link to this heading")

Prior to Matplotlib 3.10.1, when passing an array to `imshow(..., alpha=...)`, the parameter was silently ignored if the image data was an RGB or RGBA image or if `[rcParams["image.interpolation_stage"]](https://matplotlib.org/stable/users/explain/configuration.html?highlight=image.interpolation_stage#rcparam-image-interpolation-stage) ` (default: `'auto'`) resolved to "rbga".

Matplotlib 3.10.1 changed this to apply the alpha array as the alpha channel, overwriting any existing transparency information in the image data. Matplotlib 3.11.0 further fixes the handling for RGBA images: the existing alpha channel is now multiplied by the alpha array, consistent with how scalar alpha values are handled.

### Legend labels for `plot`[#](https://matplotlib.org/stable/api/prev_api_changes/api_changes_3.11.0.html#legend-labels-for-plot "Link to this heading")

Previously if a sequence was passed to the _label_ parameter of [`plot`](https://matplotlib.org/stable/api/_as_gen/matplotlib.axes.Axes.plot.html#matplotlib.axes.Axes.plot "matplotlib.axes.Axes.plot")
 when plotting a single dataset, the sequence was automatically cast to string for the legend label. Now, if the sequence length is not one an error is raised. To keep the old behavior, cast the sequence to string before passing.

### Mixing positional and keyword arguments for `legend` handles and labels...[#](https://matplotlib.org/stable/api/prev_api_changes/api_changes_3.11.0.html#mixing-positional-and-keyword-arguments-for-legend-handles-and-labels "Link to this heading")

... is no longer valid. If passing _handles_ and _labels_ to `legend`, they must now be passed either both positionally or both as keyword arguments.

### `Axes.add_collection(..., autolim=True)` updates view limits[#](https://matplotlib.org/stable/api/prev_api_changes/api_changes_3.11.0.html#axes-add-collection-autolim-true-updates-view-limits "Link to this heading")

`Axes.add_collection(..., autolim=True)` has so far only updated the data limits, and calling [`Axes.autoscale_view`](https://matplotlib.org/stable/api/_as_gen/matplotlib.axes.Axes.autoscale_view.html#matplotlib.axes.Axes.autoscale_view "matplotlib.axes.Axes.autoscale_view")
 was also necessary to update the view limits. View limits are now updated as well if `autolim=True`, using a lazy internal update mechanism, so that the costs only apply once also if you add multiple collections.

### `relim()` now accounts for Collection artists[#](https://matplotlib.org/stable/api/prev_api_changes/api_changes_3.11.0.html#relim-now-accounts-for-collection-artists "Link to this heading")

Previously, [`relim`](https://matplotlib.org/stable/api/_as_gen/matplotlib.axes.Axes.relim.html#matplotlib.axes.Axes.relim "matplotlib.axes.Axes.relim")
 did not recalculate data limits for [`Collection`](https://matplotlib.org/stable/api/collections_api.html#matplotlib.collections.Collection "matplotlib.collections.Collection")
 artists (e.g. those created by [`scatter`](https://matplotlib.org/stable/api/_as_gen/matplotlib.axes.Axes.scatter.html#matplotlib.axes.Axes.scatter "matplotlib.axes.Axes.scatter")
). Calling `ax.relim()` followed by `ax.autoscale_view()` now correctly includes scatter plots and other collections in the axes limits.

### hist2d no longer forces axes limits[#](https://matplotlib.org/stable/api/prev_api_changes/api_changes_3.11.0.html#hist2d-no-longer-forces-axes-limits "Link to this heading")

Previously, [`Axes.hist2d`](https://matplotlib.org/stable/api/_as_gen/matplotlib.axes.Axes.hist2d.html#matplotlib.axes.Axes.hist2d "matplotlib.axes.Axes.hist2d")
 would force the axes x and y limits to the extents of the histogrammed data, ignoring any other artists. [`Axes.hist2d`](https://matplotlib.org/stable/api/_as_gen/matplotlib.axes.Axes.hist2d.html#matplotlib.axes.Axes.hist2d "matplotlib.axes.Axes.hist2d")
 now behaves similarly to [`Axes.imshow`](https://matplotlib.org/stable/api/_as_gen/matplotlib.axes.Axes.imshow.html#matplotlib.axes.Axes.imshow "matplotlib.axes.Axes.imshow")
: axes limits are updated to fit the data, but autoscaling is not otherwise disabled.

### Axes.violinplot and cbook.violin\_stats ignore non-finite values[#](https://matplotlib.org/stable/api/prev_api_changes/api_changes_3.11.0.html#axes-violinplot-and-cbook-violin-stats-ignore-non-finite-values "Link to this heading")

[`violinplot`](https://matplotlib.org/stable/api/_as_gen/matplotlib.axes.Axes.violinplot.html#matplotlib.axes.Axes.violinplot "matplotlib.axes.Axes.violinplot")
 and [`matplotlib.cbook.violin_stats`](https://matplotlib.org/stable/api/cbook_api.html#matplotlib.cbook.violin_stats "matplotlib.cbook.violin_stats")
 now ignore masked and non-finite (NaN and inf) values.

### Minor log tick labels are set by number of major log ticks, not number of decades spanned[#](https://matplotlib.org/stable/api/prev_api_changes/api_changes_3.11.0.html#minor-log-tick-labels-are-set-by-number-of-major-log-ticks-not-number-of-decades-spanned "Link to this heading")

Previously, by default, on a log-scaled axis, the minor ticks would be unlabeled if the axis limits spanned more than one decade. The meaning of the _minor\_thresholds_ parameter to [`LogFormatter`](https://matplotlib.org/stable/api/ticker_api.html#matplotlib.ticker.LogFormatter "matplotlib.ticker.LogFormatter")
 has been altered so that the decision of whether to label the minor ticks is now based on the number of major ticks drawn within the axis limits.

For example, for an axis spanning from 4 to 60 (with thus a single major log tick, at 10), minor ticks are now labeled, even though the axis spans more than one decade.

### Setting titles of figures using webagg backend[#](https://matplotlib.org/stable/api/prev_api_changes/api_changes_3.11.0.html#setting-titles-of-figures-using-webagg-backend "Link to this heading")

Previously when using the `webagg` backend the title of a figure was set using `figure.set_label`. Now it is set using `figure.canvas.manager.set_window_title` which is more consistent with other backends.

### Default name of `ListedColormap`[#](https://matplotlib.org/stable/api/prev_api_changes/api_changes_3.11.0.html#default-name-of-listedcolormap "Link to this heading")

The default name of [`ListedColormap`](https://matplotlib.org/stable/api/_as_gen/matplotlib.colors.ListedColormap.html#matplotlib.colors.ListedColormap "matplotlib.colors.ListedColormap")
 has changed from "from\_list" to "unnamed".

### `font_manager.findfont` logs if selected font weight does not match requested[#](https://matplotlib.org/stable/api/prev_api_changes/api_changes_3.11.0.html#font-manager-findfont-logs-if-selected-font-weight-does-not-match-requested "Link to this heading")

When searching for a font with a weight specified, if the best-matched font differs in weight, then a warning will be logged.

### FT2Font no longer sets a default size[#](https://matplotlib.org/stable/api/prev_api_changes/api_changes_3.11.0.html#ft2font-no-longer-sets-a-default-size "Link to this heading")

In the interest of handling non-scalable fonts and reducing font initialization, the [`FT2Font`](https://matplotlib.org/stable/api/ft2font.html#matplotlib.ft2font.FT2Font "matplotlib.ft2font.FT2Font")
 constructor no longer sets a default size. Non-scalable fonts are sometimes used for bitmap-backed emoji fonts.

If metrics are important (i.e., if you are loading character glyphs, or setting a text string), then explicitly call [`FT2Font.set_size`](https://matplotlib.org/stable/api/ft2font.html#matplotlib.ft2font.FT2Font.set_size "matplotlib.ft2font.FT2Font.set_size")
 beforehand.

### `mathtext.VectorParse` now includes glyph indices[#](https://matplotlib.org/stable/api/prev_api_changes/api_changes_3.11.0.html#mathtext-vectorparse-now-includes-glyph-indices "Link to this heading")

For a _path_\-outputting [`MathTextParser`](https://matplotlib.org/stable/api/mathtext_api.html#matplotlib.mathtext.MathTextParser "matplotlib.mathtext.MathTextParser")
, in the return value of [`parse`](https://matplotlib.org/stable/api/mathtext_api.html#matplotlib.mathtext.MathTextParser.parse "matplotlib.mathtext.MathTextParser.parse")
, (a [`VectorParse`](https://matplotlib.org/stable/api/mathtext_api.html#matplotlib.mathtext.VectorParse "matplotlib.mathtext.VectorParse")
), the _glyphs_ field is now a list containing tuples of:

*   font: [`FT2Font`](https://matplotlib.org/stable/api/ft2font.html#matplotlib.ft2font.FT2Font "matplotlib.ft2font.FT2Font")
    
*   fontsize: [`float`](https://docs.python.org/3/library/functions.html#float "(in Python v3.14)")
    
*   character code: [`int`](https://docs.python.org/3/library/functions.html#int "(in Python v3.14)")
    
*   glyph index: [`int`](https://docs.python.org/3/library/functions.html#int "(in Python v3.14)")
    
*   x: [`float`](https://docs.python.org/3/library/functions.html#float "(in Python v3.14)")
    
*   y: [`float`](https://docs.python.org/3/library/functions.html#float "(in Python v3.14)")
    

Specifically, the glyph index was added after the character code.

### SVG links open in new tab or window[#](https://matplotlib.org/stable/api/prev_api_changes/api_changes_3.11.0.html#svg-links-open-in-new-tab-or-window "Link to this heading")

[`Artist.set_url`](https://matplotlib.org/stable/api/_as_gen/matplotlib.artist.Artist.set_url.html#matplotlib.artist.Artist.set_url "matplotlib.artist.Artist.set_url")
 allows to turn the Artist into a link. In SVG output, this has been implemented without specifying a [target](https://developer.mozilla.org/en-US/docs/Web/SVG/Reference/Attribute/target)
 attribute. The default target value "\_self" resulted in replacing the SVG document with the linked page when the link was clicked.

The target is now set to "\_blank" so that the link opens in a new tab or window.

### `matplotlib.testing.check_figures_equal` defaults to PNG only[#](https://matplotlib.org/stable/api/prev_api_changes/api_changes_3.11.0.html#matplotlib-testing-check-figures-equal-defaults-to-png-only "Link to this heading")

In most cases, checking that figures are equal with [`check_figures_equal`](https://matplotlib.org/stable/api/testing_api.html#matplotlib.testing.decorators.check_figures_equal "matplotlib.testing.decorators.check_figures_equal")
 does not depend on the file format. Consequently, the _extensions_ parameter now defaults to `['png']` instead of `['png', 'pdf', 'svg']`, reducing default test requirements.

### Default _style_ parameter of `image_comparison`[#](https://matplotlib.org/stable/api/prev_api_changes/api_changes_3.11.0.html#default-style-parameter-of-image-comparison "Link to this heading")

The _style_ parameter of the [`image_comparison`](https://matplotlib.org/stable/api/testing_api.html#matplotlib.testing.decorators.image_comparison "matplotlib.testing.decorators.image_comparison")
 decorator will become 'mpl20' in Matplotlib 3.13. Not passing it and relying on the previous default will warn until the change occurs.

### Windows configuration directory location[#](https://matplotlib.org/stable/api/prev_api_changes/api_changes_3.11.0.html#windows-configuration-directory-location "Link to this heading")

On Windows, the default configuration and cache directories now use `%LOCALAPPDATA%\matplotlib` instead of `%USERPROFILE%\.matplotlib`. This follows Windows application data storage conventions.

The `MPLCONFIGDIR` environment variable can still be used to override this default.

### In-place modification of colormaps[#](https://matplotlib.org/stable/api/prev_api_changes/api_changes_3.11.0.html#in-place-modification-of-colormaps "Link to this heading")

Colormaps are planned to become immutable in the long term.

As a first step, in-place modifications of colormaps are now pending-deprecated. This affects the following methods of [`Colormap`](https://matplotlib.org/stable/api/_as_gen/matplotlib.colors.Colormap.html#matplotlib.colors.Colormap "matplotlib.colors.Colormap")
:

*   [`Colormap.set_bad`](https://matplotlib.org/stable/api/_as_gen/matplotlib.colors.Colormap.html#matplotlib.colors.Colormap.set_bad "matplotlib.colors.Colormap.set_bad")
     - use `cmap.with_extremes(bad=...)` instead
    
*   [`Colormap.set_under`](https://matplotlib.org/stable/api/_as_gen/matplotlib.colors.Colormap.html#matplotlib.colors.Colormap.set_under "matplotlib.colors.Colormap.set_under")
     - use `cmap.with_extremes(under=...)` instead
    
*   [`Colormap.set_over`](https://matplotlib.org/stable/api/_as_gen/matplotlib.colors.Colormap.html#matplotlib.colors.Colormap.set_over "matplotlib.colors.Colormap.set_over")
     - use `cmap.with_extremes(over=...)` instead
    
*   [`Colormap.set_extremes`](https://matplotlib.org/stable/api/_as_gen/matplotlib.colors.Colormap.html#matplotlib.colors.Colormap.set_extremes "matplotlib.colors.Colormap.set_extremes")
     - use `cmap.with_extremes(...)` instead
    

Use the respective [`Colormap.with_extremes`](https://matplotlib.org/stable/api/_as_gen/matplotlib.colors.Colormap.html#matplotlib.colors.Colormap.with_extremes "matplotlib.colors.Colormap.with_extremes")
 and appropriate keyword arguments instead which returns a copy of the colormap (available since Matplotlib 3.4). Alternatively, if you create the colormap yourself, you can also pass the respective arguments to the constructor (available since Matplotlib 3.11).

### Contour labelling on filled contours[#](https://matplotlib.org/stable/api/prev_api_changes/api_changes_3.11.0.html#contour-labelling-on-filled-contours "Link to this heading")

Using [`clabel`](https://matplotlib.org/stable/api/_as_gen/matplotlib.axes.Axes.clabel.html#matplotlib.axes.Axes.clabel "matplotlib.axes.Axes.clabel")
 to label filled contours created with [`contourf`](https://matplotlib.org/stable/api/_as_gen/matplotlib.axes.Axes.contourf.html#matplotlib.axes.Axes.contourf "matplotlib.axes.Axes.contourf")
 is deprecated. `clabel()` is designed to label contour lines ([`Axes.contour`](https://matplotlib.org/stable/api/_as_gen/matplotlib.axes.Axes.contour.html#matplotlib.axes.Axes.contour "matplotlib.axes.Axes.contour")
), and using it with filled contours can lead to inconsistent plots. If you want to add labels to filled contours, the recommended approach is to first create the filled contours with [`contourf`](https://matplotlib.org/stable/api/_as_gen/matplotlib.axes.Axes.contourf.html#matplotlib.axes.Axes.contourf "matplotlib.axes.Axes.contourf")
, then overlay contour lines using [`contour`](https://matplotlib.org/stable/api/_as_gen/matplotlib.axes.Axes.contour.html#matplotlib.axes.Axes.contour "matplotlib.axes.Axes.contour")
, and finally apply [`clabel`](https://matplotlib.org/stable/api/_as_gen/matplotlib.axes.Axes.clabel.html#matplotlib.axes.Axes.clabel "matplotlib.axes.Axes.clabel")
 to those contour lines for labeling. For an example see [Contourf demo](https://matplotlib.org/stable/gallery/images_contours_and_fields/contourf_demo.html)
.

### `boxplot` and `bxp` _vert_ parameter, and `rcParams["boxplot.vertical"]`[#](https://matplotlib.org/stable/api/prev_api_changes/api_changes_3.11.0.html#boxplot-and-bxp-vert-parameter-and-rcparams-boxplot-vertical "Link to this heading")

The parameter _vert: bool_ has been deprecated on [`boxplot`](https://matplotlib.org/stable/api/_as_gen/matplotlib.axes.Axes.boxplot.html#matplotlib.axes.Axes.boxplot "matplotlib.axes.Axes.boxplot")
 and [`bxp`](https://matplotlib.org/stable/api/_as_gen/matplotlib.axes.Axes.bxp.html#matplotlib.axes.Axes.bxp "matplotlib.axes.Axes.bxp")
. It is replaced by _orientation: {"vertical", "horizontal"}_ for API consistency.

`rcParams["boxplot.vertical"]`, which controlled the orientation of `boxplot`, is deprecated without replacement.

### `violinplot` and `violin` _vert_ parameter[#](https://matplotlib.org/stable/api/prev_api_changes/api_changes_3.11.0.html#violinplot-and-violin-vert-parameter "Link to this heading")

The parameter _vert: bool_ has been deprecated on [`violinplot`](https://matplotlib.org/stable/api/_as_gen/matplotlib.axes.Axes.violinplot.html#matplotlib.axes.Axes.violinplot "matplotlib.axes.Axes.violinplot")
 and [`violin`](https://matplotlib.org/stable/api/_as_gen/matplotlib.axes.Axes.violin.html#matplotlib.axes.Axes.violin "matplotlib.axes.Axes.violin")
. It will be replaced by _orientation: {"vertical", "horizontal"}_ for API consistency.

### Arbitrary code in `axes.prop_cycle` rcParam strings[#](https://matplotlib.org/stable/api/prev_api_changes/api_changes_3.11.0.html#arbitrary-code-in-axes-prop-cycle-rcparam-strings "Link to this heading")

The `axes.prop_cycle` rcParam accepts Python expressions that are evaluated in a limited context. The evaluation context has been further limited and some expressions that previously worked (list comprehensions, for example) no longer will. This change is made without a deprecation period to improve security. The previously documented cycler operations at [https://matplotlib.org/cycler/](https://matplotlib.org/cycler/)
 are still supported.

### Capitalization of None in matplotlibrc[#](https://matplotlib.org/stable/api/prev_api_changes/api_changes_3.11.0.html#capitalization-of-none-in-matplotlibrc "Link to this heading")

In `matplotlibrc` config files every capitalization of None was accepted for denoting the Python constant [`None`](https://docs.python.org/3/library/constants.html#None "(in Python v3.14)")
. This is now deprecated, and the only accepted capitalization is None, i.e., starting with a capital letter and all other letters in lowercase.

### Third-party scales no longer need to have an _axis_ parameter[#](https://matplotlib.org/stable/api/prev_api_changes/api_changes_3.11.0.html#third-party-scales-no-longer-need-to-have-an-axis-parameter "Link to this heading")

Since Matplotlib 3.1 [PR 12831](https://github.com/matplotlib/matplotlib/pull/12831)
 scale objects should be reusable and therefore independent of any particular Axis. Therefore, the use of the _axis_ parameter in the `__init__` had been discouraged. However, having that parameter in the signature was still necessary for API backwards-compatibility. This is no longer the case.

[`register_scale`](https://matplotlib.org/stable/api/scale_api.html#matplotlib.scale.register_scale "matplotlib.scale.register_scale")
 now accepts scale classes with or without this parameter.

The _axis_ parameter is pending-deprecated. It will be deprecated in Matplotlib 3.13, and removed in Matplotlib 3.15.

Third-party scales are recommended to remove the _axis_ parameter now if they can afford to restrict compatibility to Matplotlib >= 3.11 already. Otherwise, they may keep the _axis_ parameter and remove it in time for Matplotlib 3.13.

### `matplotlib.style.core`[#](https://matplotlib.org/stable/api/prev_api_changes/api_changes_3.11.0.html#matplotlib-style-core "Link to this heading")

The `matplotlib.style.core` module is deprecated. All APIs intended for public use are now available in [`matplotlib.style`](https://matplotlib.org/stable/api/style_api.html#module-matplotlib.style "matplotlib.style")
 directly (including `USER_LIBRARY_PATHS`, which was previously not reexported).

The following APIs of `matplotlib.style.core` have been deprecated with no replacement: `BASE_LIBRARY_PATH`, `STYLE_EXTENSION`, `STYLE_BLACKLIST`, `update_user_library`, `read_style_directory`, `update_nested_dict`.

### Font hinting and kerning factors[#](https://matplotlib.org/stable/api/prev_api_changes/api_changes_3.11.0.html#font-hinting-and-kerning-factors "Link to this heading")

Due to internal changes to support complex text rendering, the hinting factor and kerning factor on fonts are no longer used. Setting the `text.hinting_factor` or `text.kerning_factor` rcParams (the latter of which existed only for backwards-compatibility) to any value other than None is deprecated, and they will be removed in the future.

Likewise, passing the `hinting_factor` argument to the [`FT2Font`](https://matplotlib.org/stable/api/ft2font.html#matplotlib.ft2font.FT2Font "matplotlib.ft2font.FT2Font")
 constructor is deprecated.

### `FT2Image` image buffer[#](https://matplotlib.org/stable/api/prev_api_changes/api_changes_3.11.0.html#ft2image-image-buffer "Link to this heading")

Use 2D uint8 ndarrays instead. In particular:

*   The `FT2Image` constructor took `width, height` as separate parameters but the ndarray constructor takes `(height, width)` as single tuple parameter.
    
*   [`FT2Font.draw_glyph_to_bitmap`](https://matplotlib.org/stable/api/ft2font.html#matplotlib.ft2font.FT2Font.draw_glyph_to_bitmap "matplotlib.ft2font.FT2Font.draw_glyph_to_bitmap")

#### Image path semantics of toolmanager-based tools[#](https://matplotlib.org/stable/api/prev_api_changes/api_changes_3.11.0.html#image-path-semantics-of-toolmanager-based-tools "Link to this heading")

Previously, MEP22 ("toolmanager-based") Tools would try to load their icon (`tool.image`) relative to the current working directory, or, as a fallback, from Matplotlib's own image directory. Because both approaches are problematic for third-party tools (the end-user may change the current working directory at any time, and third-parties cannot add new icons in Matplotlib's image directory), this behavior has been removed; instead, `tool.image` is now interpreted relative to the directory containing the source file where the `Tool.image` class attribute is defined. (Defining `tool.image` as an absolute path also works and is compatible with both the old and the new semantics.)

### Glyph indices now typed distinctly from character codes[#](https://matplotlib.org/stable/api/prev_api_changes/api_changes_3.11.0.html#glyph-indices-now-typed-distinctly-from-character-codes "Link to this heading")

Previously, character codes and glyph indices were both typed as [`int`](https://docs.python.org/3/library/functions.html#int "(in Python v3.14)")
, which means you could mix and match them erroneously. While the character code can't be made a distinct type (because it's used for [`chr`](https://docs.python.org/3/library/functions.html#chr "(in Python v3.14)")
/[`ord`](https://docs.python.org/3/library/functions.html#ord "(in Python v3.14)")
), typing glyph indices as a distinct type means these can't be fully swapped.

On this page
